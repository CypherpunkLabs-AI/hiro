# GCP TDX boot image

`image/mkosi.conf` builds the UEFI boot disk, including the exact proxy container. `scripts/stage-image` verifies the pulled digest against Docker's registry identity, saves the container locally and records its content-addressed config ID. CI first authenticates both the OCI image and its metadata with GitHub's attestation verifier. Executable assets and public security policy are embedded in the dm-verity-protected root filesystem; deployment credentials come from a separate configuration disk.

There are two manifests to avoid a self-referential disk hash. The embedded `release.json` identifies the Compose configuration and container digests. The external signed `image-release.json` identifies the finished disk, archive, UKI, kernel, initrd, root hash and embedded release. The latter is built after finalizing the disk. Clients must verify the external signature and actual boot evidence; checking the application RTMR alone does not prove that the approved OS ran.

The UKI embeds the kernel, initrd and root-hash command line. The image profile uses measured boot with Secure Boot disabled. Acceptance requires Intel DCAP verification and validation of the actual GCP firmware/CCEL/boot chain against the approved release, including executable boot artifacts and effective command line. Platform measurements are not fabricated in CI or inferred merely from the `TDX_CAPABLE` image feature.

The immutable startup program mounts volatile runtime storage, verifies its embedded assets, loads the local container without network pulls, and starts the unprivileged Compose service. Docker save/load does not preserve registry RepoDigests, so the launcher selects the exact recorded image config ID using a generated in-memory Compose override. Both the archive and ID are covered by the protected root hash. Public security policy is baked into that root; application credentials are not.

Systemd mounts the required ext4 filesystem labelled `hiro-config` at `/mnt/config` read-only with `nosuid,nodev,noexec`, before `hiro.service` runs. The service requires a readable, nonempty `secrets.env`. Compose loads it as a raw service `env_file`, preserving literal credential values without interpolation. The immutable Compose environment takes precedence for measured endpoint/trust policy and runtime paths. The disk is not mounted inside the proxy container, and Docker state remains volatile. Configuration-disk contents are not covered by the boot image's dm-verity root or release measurements. This is a plaintext deployment configuration mechanism, not attestation-gated secret delivery.

On TDX, the launcher extends an initially zero RTMR3 exactly once with `SHA384(b"hiro.release.v1\0" + exact_release_bytes)`. RTMR3 becomes `SHA384(zero_48_bytes + event_digest)`. A same-boot restart accepts only that exact existing measurement. It provisions the dedicated Linux TSM report entry, delegates its attributes to UID 65532, and bind-mounts it at `/run/hiro/tdx-report`. The proxy receives this entry and read-only release/CCEL evidence, not host privileges or a Docker socket.

A non-TDX UEFI boot may start the process for CI validation, but the proxy rejects readiness, hardware evidence and attested sessions. CI blocks outbound ACME traffic and checks the TLS listener's rejection of TLS 1.2, plaintext HTTP and connections without an issued certificate. There is no synthetic quote, test certificate or verification bypass in the published image. A fresh external verifier must check the challenge/keyset binding, DCAP signatures and TCB status, approved boot chain, signed image release, RTMR3 and the Oak handshake key binding before trusting a real deployment.

TLS terminates in the unprivileged proxy on port 8443, published as TCP 443. Rustls allows TLS 1.3 only, with no early data, key logging, secret extraction or resumption. The ACME client generates ECDSA P-256 keys, answers TLS-ALPN-01 and renews certificates. A dedicated non-swappable tmpfs caches private certificate/account state across container restarts; VM restart destroys it. The launcher disables swap before startup and the proxy checks the cache mount and permissions. The selected certificate is frozen for each connection, and its SPKI digest and domain enter the same keyset used by attestation and receipts. Renewals affect new connections without changing existing identities.

The proxy generates ephemeral service keys inside guest memory. No local KMS, Phala host runtime or evidence worker is used. Verification of remote Phala confidential inference remains independent. Client integration and real upstream credentials are separate from boot-image publication; the image build cannot certify a hardware boot it has not observed.
